# 04 — ข้อตกลงการทำงานของทีม (Team Working Agreement)

## 1. หลักใหญ่: อิสระภายใน — สัญญาภายนอกคงที่
ทุกคน **ออกแบบภายในโมดูลของตัวเองได้ตามแนวทางของตัวเอง** (algorithm, โครงสร้างโค้ด, UI, วิธีทดสอบ) — ทีมจะไม่บังคับให้ทุกคนใช้วิธีเดียวกัน
แต่ **สัญญาการเชื่อมต่อ C0–C4** (`03_SHARED_API_CONTRACTS.md`) ต้อง **เข้ากันได้ย้อนหลัง** เสมอ และการเปลี่ยนที่กระทบคนอื่นต้อง **แจ้ง P4 ก่อนลงมือ**

## 2. ระดับการเปลี่ยนแปลง GREEN / YELLOW / RED

| ระดับ | ความหมาย | ต้องทำอะไร | ตัวอย่าง |
|---|---|---|---|
| 🟢 **GREEN** | เปลี่ยนรายละเอียดภายในไฟล์ที่ตัวเองเป็นเจ้าของ โดย **ไม่เปลี่ยน** สิ่งที่โมดูลอื่นเห็น | ทำได้เลยบน branch ตัวเอง → PR ปกติ (ไม่ต้องขออนุญาตล่วงหน้า) | P1 เปลี่ยน detector/ROI/threshold ใน `cv/**` แต่ยังส่ง payload ตาม C1 · P2 refactor `services.py` / เพิ่ม index ใน DB โดย JSON เท่าเดิม · P3 redesign หน้า/สี/layout โดยใช้ API เดิมและกฎแสดงผล C2 · P4 ปรับ Staff Console / เพิ่ม test |
| 🟡 **YELLOW** | กระทบโมดูลอื่นหรือสัญญา แต่ **เพิ่มแบบ backward-compatible** (field ใหม่แบบ optional, endpoint ใหม่, env ใหม่) หรือแก้ไฟล์ที่ต้องมี approval ร่วม | **แจ้ง P4 + เจ้าของที่เกี่ยวข้องก่อนลงมือ** ด้วย Change Request (`06_…`) → ได้คำตอบ “ตกลง” → ทำ + test + อัปเดตสัญญาใน PR เดียวกัน → reviewer จากฝั่งที่ได้รับผลกระทบ approve | P2 เพิ่ม `SL_CV_EVIDENCE_DIR` (PA-01) · P2 เพิ่ม field ใหม่ใน SeatView · P4 สร้าง `SeatCheckPanel` (PA-05) · P1 ขอ seat/กล้องใหม่ · P3 แก้ `live.tsx` · ใครก็ตามแก้ `package.json`, `requirements.txt`, `conftest.py`, `playwright.config.ts` |
| 🔴 **RED** | เปลี่ยนแบบ **ไม่เข้ากันได้** หรือเปลี่ยนสถาปัตยกรรม | CR + **ทั้งทีมอนุมัติ (4/4) เป็นลายลักษณ์อักษรใน Issue** ก่อนเริ่ม + แผน migration + แผน rollback | ลบ/เปลี่ยนชื่อ route หรือ field, เปลี่ยนความหมาย enum (`reserved`, `unknown` …), เปลี่ยน DB จาก SQLite, ให้ CV ตัดสินสถานะสุดท้ายเองแทน engine, เพิ่มที่นั่งจริงลงผังนักศึกษา (PA-03), เปลี่ยนกฎความปลอดภัย (เช่น ให้ stale/unknown ถูกแนะนำ) |

**ถ้าไม่แน่ใจว่าเป็นระดับไหน → ถือว่าเป็น YELLOW และถาม P4**

## 3. กติกาการแจ้งล่วงหน้า (สำคัญที่สุด)
1. ก่อนทำงานที่ **กระทบโมดูลอื่น** ต้องแจ้ง P4 **ก่อนเขียนโค้ด** (Issue label `integration` + ใช้ template CR)
2. P4 ตอบภายใน 1 วันทำการ: ✅ ตกลง (ระบุระดับ) / ❓ ขอข้อมูลเพิ่ม / ⛔ ไม่ตกลง (พร้อมเหตุผลและทางเลือก)
3. RED ต้องได้ approve ครบ 4 คนใน Issue
4. งานที่ทำไปก่อนได้รับตอบ **เสี่ยงถูกปฏิเสธตอน merge** — ไม่ใช่ความผิดของ P4

## 4. ความเป็นเจ้าของไฟล์และการแก้บั๊ก
* เจ้าของไฟล์ดูที่ `docs/team_v3/OWNERSHIP_MAP.csv` (ตรวจด้วย `python scripts/check_ownership.py --owner P# --base origin/main`)
* **ห้ามแก้โค้ดภายในของคนอื่น** แม้จะเห็นวิธีแก้ — ให้เปิด Issue `bug` ถึงเจ้าของพร้อม (1) ขั้นตอนทำซ้ำ (2) ผลจริง/log (3) ผลที่คาด (4) contract ข้อไหนที่ผิด
* **Owner-led fix:** เจ้าของโมดูลเป็นคนแก้; P4 ช่วยเขียน test ที่จับบั๊กได้ (ในไฟล์ของ P4) ได้
* ข้อยกเว้น: P4 อาจเขียน **adapter** ใน `integration/**` เพื่อเชื่อมโมดูลที่เข้ากันไม่ได้ **ชั่วคราว** โดยไม่แก้ไฟล์ของเจ้าของ — และต้องเปิด Issue ให้เจ้าของแก้ถาวร
* ถ้าโมดูลละเมิดสัญญาและแก้ไม่ทันก่อนนำเสนอ: P4 **ไม่ merge** ส่วนนั้น และรายงานเป็นข้อจำกัด (ไม่ซ่อน)

## 5. ความซื่อสัตย์และความเป็นส่วนตัว (ไม่มีข้อยกเว้น)
* ห้ามแต่งผลทดสอบ, screenshot, ผลตรวจจับ, ตัวเลขความแม่นยำ, ความคืบหน้า — ห้ามติ๊ก PASS ถ้าไม่ได้รันจริง
* ข้อมูลจำลองต้องติดป้าย SIMULATION; ห้ามนำเสนอว่าเป็นผลกล้องจริง
* ภาพ/วิดีโอบุคคลใช้ได้เฉพาะเมื่อได้รับอนุญาตเป็นลายลักษณ์อักษร และ **ไม่ commit** ลง Git; ไม่เชื่อม CCTV มหาวิทยาลัย; ไม่ deploy สู่ public network
* ห้าม commit token/password/`.env`/DB/weights/วิดีโอ
* เครดิตตามงานจริง: งาน V2 เป็น baseline ร่วม — ห้ามอ้างว่าเพื่อนเขียนส่วนที่ไม่ได้เขียน และระบุส่วนที่ AI ช่วยใน PR

## 6. Git workflow ย่อ
* branch ของตัวเอง: P1 `feature/v3-cv` · P2 `feature/v3-backend` · P3 `feature/v3-student` · P4 `feature/v3-staff-qa` (แตก branch ย่อยได้ เช่น `feature/v3-cv-roi`)
* `git fetch origin && git merge origin/main` อย่างน้อยวันละครั้ง
* PR เข้า `main` ใช้ `.github/pull_request_template.md`; P4 เป็นคนเดียวที่ merge (Squash and merge) หลังผ่าน `FINAL_INTEGRATION_PLAYBOOK_TH.md`
* ห้าม force-push branch ร่วม (`main`), ห้าม push ตรงเข้า `main`
* ไฟล์ FROZEN V2 ห้ามแก้ — ผลทดสอบไป `artifacts/` (git-ignored), หลักฐานที่คัดแล้วไป `evidence/team_v3/<role>/`

## 7. การสื่อสาร
* Stand-up ในแชทกลุ่มทุกเย็น 4 บรรทัด: ทำอะไร/commit-PR · พรุ่งนี้ทำอะไร · ติดอะไร/ต้องการอะไรจากใคร · หลักฐาน/ผลทดสอบ
* เรื่องที่ต้องตัดสินใจ/ติดตาม → GitHub Issue (ไม่ใช่แชท) เพื่อให้มีบันทึก
* ติดขัด > 1 วัน → label `blocked` + แจ้ง P4
